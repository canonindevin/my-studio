Margin reconciliation workbook

Four principles for bridging grains of data

Enter your own brands, SKUs and customer sales. Follow or break each principle, then arrange brand, SKU and customer into any hierarchy and see how each number reaches each level.

Your sources

Every cell is editable. Rename things, change amounts, add or remove rows. A grain is what one row stands for, so each table states its own.

Marketing spend

One row per brand. Knows nothing about customers.

Standard cost

One row per SKU. Brand is an attribute of the SKU.

Sales and freight

One row per customer and SKU. The lowest grain. Price is per unit, freight is the total for the row.

The principles

Each one has a switch. The worked figure beside it is built from your numbers.

Principle 1

A total never travels down a grain. A rate can.

A cost that moves with volume is turned into a per-unit rate at the grain where it lives. The rate is then multiplied by the volume on each lower-grain row. A rate repeated on many rows does no harm. A total repeated on many rows is counted once per row.

    Principle 2

    A cost with no link to the row needs a named driver, or it stays where it was recorded.

    Marketing was never spent per customer, so no rate exists. To bring it down you choose a driver and split the total by each row's share. The total is preserved under any driver. The split is your assumption. Leaving it at brand level assumes nothing.

      Principle 3

      Ratios are rebuilt from sums at every level. They are never averaged.

      Margin %, price per unit and cost per unit are all ratios. When rows roll up, sum the numerator and the denominator separately and divide again. Averaging row percentages gives a small row the same weight as a large one.

        Principle 4

        Every bridged number ties to its source, or to a reconciling item you can name.

        This one has no switch. It is the test of the other three. Each measure's total in the model is compared with the total of the file it came from. A difference is either zero, a named item such as unsold stock, or an error.

            ✓ Works

            ' tblCost, one row per SKU
UnitCost  = [@TotalCost] / [@Volume]

' tblSales, one row per customer and SKU
Brand     = XLOOKUP([@SKU], tblSKU[SKU], tblSKU[Brand])
COGS      = [@Units] * XLOOKUP([@SKU], tblCost[SKU], tblCost[UnitCost])
Marketing = XLOOKUP([@Brand], tblMkt[Brand], tblMkt[Spend])
            * [@NetSales] / SUMIFS([NetSales], [Brand], [@Brand])

' Tie-out cell, must be zero
= SUM(tblSales[Marketing]) - SUM(tblMkt[Spend])
            • Look up the rate, never the total. The rate is the same on every row of a SKU, so repeating it does no harm.
            • The SUMIFS denominator is the brand's total sales, so each brand's shares add to 100%.
            • For margin % in a PivotTable, add a calculated field = GrossMargin / NetSales. It divides the sums.

            ✕ Breaks

            ' Total repeated on every customer row of the SKU
COGS      = XLOOKUP([@SKU], tblCost[SKU], tblCost[TotalCost])

' Brand spend repeated on every row of the brand
Marketing = XLOOKUP([@Brand], tblMkt[Brand], tblMkt[Spend])

' PivotTable value set to "Average of GM %"
            • Each row looks reasonable on its own. The error only shows when a PivotTable or SUM adds the column.
            • An average of row percentages weights a small customer the same as a large one.
            • A SKU missing from tblCost returns #N/A. Do not wrap it in IFERROR(…, 0), which turns a missing cost into a 100% margin.

            ✓ Works

            // 1. Rate at the SKU grain, before any merge
CostRate = Table.AddColumn(Cost, "UnitCost",
    each [TotalCost] / [Volume], type number),

// 2. Merge onto Sales by SKU, expand UnitCost and Brand only
Merged  = Table.NestedJoin(Sales, {"SKU"}, CostRate, {"SKU"},
    "c", JoinKind.LeftOuter),
Sales2  = Table.ExpandTableColumn(Merged, "c", {"UnitCost", "Brand"}),
WithCogs = Table.AddColumn(Sales2, "COGS",
    each [Units] * [UnitCost], type number),

// 3. Brand sales total, used as the allocation base
BrandBase = Table.Group(WithCogs, {"Brand"},
    {{"BrandSales", each List.Sum([NetSales]), type number}}),

// 4. Merge BrandBase and Marketing by Brand, then
//    Marketing = [Spend] * [NetSales] / [BrandSales]
            • Compare Table.RowCount before and after every merge. If the count grows, the lookup side has duplicate keys and rows have fanned out.
            • Group By is how you move a measure up a grain. Do it before merging, so both sides of the merge sit at the same grain.

            ✕ Breaks

            // Expanding the total instead of the rate
Table.ExpandTableColumn(Merged, "c", {"TotalCost"})

// Merging Marketing (brand) straight onto Sales
// and expanding [Spend] as if it were a row value
            • The row count stays the same in both cases, so the row-count check passes. Only a control total catches a repeated value.
            • A left join from Sales drops any brand that had spend but no sales. Its marketing disappears from the model. Compare List.Sum of the allocated column with the source total.
            • Inner joins drop sales rows whose SKU has no cost record. Use a left join and inspect the nulls.

            ✓ Works

            Model, single-direction filters, one to many:
  Brand    1 ─► *  SKU       1 ─► *  Sales
  Brand    1 ─► *  Marketing
  Customer 1 ─► *  Sales
SKU[UnitCost] holds the rate.

Net Sales = SUM ( Sales[NetSales] )

COGS =
SUMX ( Sales, Sales[Units] * RELATED ( SKU[UnitCost] ) )

Marketing Spend = SUM ( Marketing[Spend] )

Marketing Allocated =
SUMX (
    VALUES ( Brand[Brand] ),
    VAR Spend      = [Marketing Spend]
    VAR SalesHere  = [Net Sales]
    VAR SalesBrand =
        CALCULATE ( [Net Sales],
            REMOVEFILTERS ( Customer ), REMOVEFILTERS ( SKU ) )
    RETURN DIVIDE ( Spend * SalesHere, SalesBrand )
)

GM % = DIVIDE ( [Net Sales] - [COGS], [Net Sales] )
            • Keep each fact at its own grain and let shared dimensions connect them. Sales and Marketing never relate to each other directly.
            • SUMX multiplies row by row and then sums, so COGS is right at every level of a visual.
            • If standard cost changes by period, keep it as a fact keyed by SKU and period and look the rate up on both.

            ✕ Breaks

            -- [Marketing Spend] in a table by Customer:
-- the full brand total repeats on every row,
-- because Customer does not filter Marketing.

-- Sales[Units] * SKU[TotalCost] as a calculated
-- column, or SUM ( SKU[TotalCost] ) by Customer.

-- A Sales-to-Marketing relationship on Brand
-- (many to many), or bidirectional filters
-- switched on to make the numbers move.

-- GM % = AVERAGE ( Sales[GMPct] )
            • A repeated total is Power BI telling you the measure does not exist at that grain. Either allocate it with a measure or show it only by brand.
            • Bidirectional and many-to-many relationships make the numbers change with the filter, which looks like a fix. The results are hard to predict and rarely tie.
            • Ratios belong in measures built from sums. A stored percentage column cannot be re-aggregated.
