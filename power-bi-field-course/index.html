    From raw exports to reports people trust

    A self-paced course in Power Query and Power BI. Each module gives you the idea, a lab you can click through right here, a task to do in the real tool, and a short check. Your progress is saved in this browser.

    Map

    How the pieces fit

    Every Power BI report moves through the same six stages. Select a stage to see what happens there and which module covers it.

    Two tools, one workflow

    Power Query is the data preparation engine. It connects to sources, cleans and reshapes them, and records every action as a repeatable step. The same engine runs inside Excel (Data → Get Data), Power BI Desktop (Transform data) and dataflows, so the skill carries across all three.

    Power BI takes the prepared tables, relates them in a data model, calculates with DAX measures, and presents the results as interactive reports you publish and share.

    Most of the value comes from the first half. A clean model makes the formulas short and the visuals easy. A messy one makes everything after it harder.

    Module 1 · Power Query · 2 hrs

    Clean data once, refresh forever

    Power Query replaces the manual clean-up you repeat every week or month. You do the work once, it records the recipe, and the next file runs through the same steps with one click.

    • Connect to a file and open the editor
    • Read and edit the Applied Steps list
    • Use the eight transforms that cover most clean-up
    • Set data types and spot quality problems

    The editor in four parts

    • Queries pane (left). One query per table you are building.
    • Preview (centre). A sample of the data at the selected step.
    • Ribbon (top). Home has the everyday actions, Transform changes columns in place, Add Column creates new ones.
    • Applied Steps (right). The recipe. Select a step to see the data at that point. Rename, reorder or delete steps here.

    Your source is never changed. Power Query reads it, applies the steps to a copy, and loads the result.

      Combine, reshape and automate
      
  
      Real work rarely lives in one tidy file. This module covers stacking tables, joining them, loading whole folders, and reading the M code behind your steps so you can fix it when the ribbon runs out.

      Append stacks, Merge joins
      
    
      Append puts tables on top of each other. Use it when the tables have the same columns: January, February and March sales. Merge puts tables side by side by matching a key column. Use it to bring in something a table lacks: a product category, a manager name, a target.

      Load a whole folder
      
    
      If someone drops a new file into a folder each month, connect to the folder, not the file. Get Data → Folder, filter to the files you want, then select Combine Files. Power Query builds a sample query and a function, then applies it to every file. Next month's file is picked up on refresh with no changes from you.
      
    
      For this to hold, the files need the same layout. Filter on extension and name so a stray document in the folder does not break the refresh.
      

    
      Reading M
      
    
      Every step you click becomes a line of M. You do not need to write M from scratch, but being able to read it turns a broken refresh from a mystery into a five-minute fix.
      
  
      

      let
    Source   = Csv.Document(File.Contents("C:\Data\orders.csv"), [Delimiter=",", Encoding=65001]),
    Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    Typed    = Table.TransformColumnTypes(Promoted, {{"Amount", type number}, {"OrderDate", type date}}),
    Recent   = Table.SelectRows(Typed, each [OrderDate] >= #date(2025, 1, 1))
in
    Recent
      
  
      
    
        
      
      • let … in wraps a list of named steps. The name after in is what the query returns.
        • 
      
      • Each step usually takes the previous step's name as its first argument. That is how the chain connects.
        • 
      
      • each [OrderDate] >= … means "for each row, test this". [Column] reads a column in the current row.
        • 
      
      • M is case-sensitive. Table.SelectRows works; table.selectrows does not. Keywords such as if, then, else are lowercase.
        • 
      
      • Step names with spaces are written #"Removed Top Rows".
        • 
    
      
    
      Custom columns
      
    
      Add Column → Custom Column takes one M expression:
      
  
      

      if [Sales] >= 1000 then "High" else "Standard"

try Number.From([Quantity]) otherwise null      // survive bad values instead of erroring

Text.Upper(Text.Trim([Region]))                 // normalise text before matching
      
  
      
    
      Before writing M, try Column From Examples. You type the result you want for a few rows and Power Query works out the formula.
      

    
      Parameters and functions
      
    
      A parameter (Manage Parameters) is a named value such as a folder path or a start date. Use one wherever you would otherwise hard-code something that differs between your machine and someone else's. A function is a query that takes inputs, so the same clean-up can run on many tables:
      
  
      

      (path as text) as table =>
let
    Source   = Csv.Document(File.Contents(path), [Delimiter=",", Encoding=65001]),
    Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars=true])
in
    Promoted
      
  
      
    
      Query folding
      
    
      When the source is a database, Power Query tries to translate your steps into one query that the database runs. This is query folding, and it is the difference between a refresh that takes seconds and one that pulls every row across the network first.
      
    
        
      
      • Filter rows and remove columns as early as possible. Those steps fold well.
        • 
      
      • Right-click a step and look for View Native Query. If it is available, folding is still working at that step.
        • 
      
      • Steps such as adding an index column or some custom M can stop folding. Put them late.
        • 
    
      
    
      Organise your queries
      
    
        
      
      • Reference creates a new query that starts from another one's result. Use it to build several tables from one cleaned source. Duplicate copies the steps and has no link back.
        • 
      
      • Turn off Enable load on helper queries so they do not appear in the model.
        • 
      
      • Group queries into folders: Sources, Staging, Model.
        • 
    
      
  
      

  
      Straight talk. M looks intimidating, and plenty of capable people avoid the Advanced Editor for years because of it. You already know more than you think: every line there is a step you clicked. Open it after each lab and read your own steps back. Ten minutes of that, a few times, and it stops being a wall.

  Module 3 · Data model · 2 hrs
  
      Build a star schema
      
  
      The model is where Power BI stops being a spreadsheet. A handful of well-related tables is what lets one slicer filter every visual on a page and keeps your formulas short.
      
  
        
    
      • Tell fact tables from dimension tables
        • 
    
      • Create one-to-many relationships
        • 
    
      • Understand which way filters flow
        • 
    
      • Add a proper date table
        • 
  
      
  
      
    
      Facts and dimensions
      
    
      A fact table records events or measurements: order lines, payments, tickets, daily stock counts. It is long, mostly numbers and keys, and you aggregate it. A dimension table describes the things involved: products, customers, dates, stores. It is short, has one row per item, and you filter and group by it.
      
    
      Arrange them as a star: the fact in the middle, each dimension linked to it by a single key column.
      
  
      

  
      
    
      Lab
      Follow the filter
      
    
      Select a table. Relationships run from the "1" side to the "many" (*) side, and filters travel in that direction.
      
    
      
      
      
      
    
      
  
      

  
      
    
      Lab
      Fact or dimension?
      Decide for each table.
      
    
      
  
      

  
      
    
      Relationship settings
      
    
        
      
      • Cardinality: aim for one-to-many, with the dimension on the "one" side. The key in the dimension must be unique.
        • 
      
      • Cross-filter direction: keep it Single. Bidirectional filters can produce ambiguous paths and surprising totals; use them only for a specific reason.
        • 
      
      • Many-to-many usually means a dimension is missing. Build the missing table of unique keys in Power Query.
        • 
      
      • Only one relationship between two tables can be active. If a fact has an order date and a ship date, the second relationship is inactive and you switch it on inside a measure with USERELATIONSHIP.
        • 
    
      
    
      The date table
      
    
      Create one dedicated date table with a row for every day across your data's range, plus columns for year, quarter, month name and month number. Relate it to the date key in each fact. Then select Mark as date table. Time calculations such as year-to-date depend on it.
      
    
      Set month name to Sort by column month number, or your charts will run April, August, December.
      
    
      Tidy the model for the people using it
      
    
        
      
      • Hide key columns and anything users should not drag onto a visual.
        • 
      
      • Use plain names: "Order Date", not "ord_dt".
        • 
      
      • Set formats (currency, percent, thousands separator) once on the column or measure.
        • 
    
      
  
      
  
      Straight talk. The one big flat table feels natural if you come from Excel, and it will work for a while. Then a second data source arrives, the totals stop adding up, and the formulas turn into workarounds. Splitting into facts and dimensions feels like extra effort up front. It is the step people most often wish they had done from the start.
      
  
      
    
      Do it for real
      Your turn
      
    
        
      
      • From one flat table, use Reference and Remove Duplicates in Power Query to create a product (or customer) dimension.
        • 
      
      • Create a date table and mark it as the date table.
        • 
      
      • In Model view, create the relationships and confirm each is one-to-many, single direction.
        • 
      
      • Hide the key columns in the fact table.

  Module 4 · DAX · 4 hrs
  
      Measures and filter context
      
  
      DAX is the formula language of the model. The functions are easy to look up. The idea that takes practice is filter context: the same measure gives a different answer in every cell because each cell filters the data differently.
      
  
        
    
      • Choose a measure or a calculated column
        • 
    
      • Explain filter context for any cell
        • 
    
      • Change context with CALCULATE
        • 
    
      • Write time comparisons and safe ratios
        • 
  
      
  
      
    
      Measure or calculated column?
      
    
      A calculated column is computed row by row at refresh and stored. Use it when you need a value to slice or group by, such as an age band. A measure is computed at query time for whatever is on screen. Use it for anything you aggregate: totals, averages, ratios, comparisons. When in doubt, write a measure. If the column could be made in Power Query instead, make it there.
      
  
      

      Total Sales = SUM ( Sales[Amount] )

Margin % =
VAR Revenue = SUM ( Sales[Amount] )
VAR Cost    = SUM ( Sales[Cost] )
RETURN
    DIVIDE ( Revenue - Cost, Revenue )
      
  
      
    
      DIVIDE returns blank instead of an error when the denominator is zero. VAR names an intermediate result so the formula reads top to bottom and each part is calculated once.

      CALCULATE
      
    
      CALCULATE evaluates an expression after changing the filter context. It can add a filter, replace one, or remove one. Almost every non-trivial measure uses it.
      
  
      

      Bike Sales       = CALCULATE ( [Total Sales], Product[Category] = "Bikes" )
All-Region Sales = CALCULATE ( [Total Sales], REMOVEFILTERS ( Region[Region] ) )
Sales YTD        = TOTALYTD ( [Total Sales], 'Date'[Date] )
Sales PY         = CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
Rolling 12M      = CALCULATE ( [Total Sales],
                       DATESINPERIOD ( 'Date'[Date], MAX ( 'Date'[Date] ), -12, MONTH ) )
      
  
      
    
      Iterators
      
    
      SUM adds up one column. When the value has to be computed per row first, use an iterator such as SUMX, which walks a table row by row and then adds the results:
      
  
      

      Revenue = SUMX ( Sales, Sales[Quantity] * Sales[Unit Price] )
      
  
      
    
      Working practices
      
    
        
      
      • Build measures on measures. Define [Total Sales] once and reuse it everywhere.
        • 
      
      • Keep measures in a dedicated table or display folders so people can find them.
        • 
      
      • Test each measure in a plain matrix against a number you can verify by hand before it goes on a report.
        • 
      
      • Write measure references without the table ([Total Sales]) and column references with it (Sales[Amount]).
        • 
    
      
  
      
  
      Straight talk. DAX is where most learners stall, and it is rarely about intelligence. It is usually one of two things: the model underneath is not a star, or filter context has not clicked yet. If a measure will not behave, resist piling on more functions. Go back and ask, "what filters are on this cell?" Being patient with that question is how the skill arrives.
      
  
      
    
      Do it for real

        • 
      
      • Write a percent-of-total measure using REMOVEFILTERS or ALL.
        • 
      
      • Rewrite one measure using VAR and RETURN.

  Module 5 · Reports · 2 hrs
  
      Design reports people can read
      
  
      A report has a few seconds to answer the question its reader brought to it. Choose the visual for the question, give the page a clear order, and let interaction carry the detail.
      
  
        
    
      • Match a visual to the question
        • 
    
      • Lay out a page with a clear reading order
        • 
    
      • Use slicers, drill-through, tooltips and bookmarks
        • 
    
      • Apply conditional formatting with restraint
        • 
  
      

  
      
    
      Lab
      Which visual?
      Start from what the reader needs to see.
      
    
      
    
      
      
      
      
      
    
      
  
      

  
      
    
      Page layout
      
    
        
      
      • Top left is read first. Put the headline numbers there as cards, then the main chart, then supporting detail.
        • 
      
      • One question per page. Five to eight visuals is plenty.
        • 
      
      • Align to a grid and keep spacing even. Use the Format → Align tools.
        • 
      
      • Title each visual with what it shows: "Revenue by month, 2025 vs 2024", not "Chart 3".
        • 
      
      • Use colour to mean something. One neutral colour for most bars and one accent for the item that matters reads better than a rainbow.
        • 
      
      • Check contrast and add alt text so the report works for everyone.
        • 
    
      
    
      Interaction
      
    
        
      
      • Slicers filter the page. Use the Sync slicers pane to carry a selection across pages.
        • 
      
      • Cross-filtering: selecting a bar filters the other visuals. Use Edit interactions to switch between filter, highlight and none for each pair.
        • 
      
      • Drill down moves through a hierarchy inside one visual, such as year to quarter to month.
        • 
      
      • Drillthrough jumps to a detail page filtered to the item you right-clicked.
        • 
      
      • Report page tooltips show a small custom page on hover.
        • 
      
      • Bookmarks save a view of the page. Pair them with buttons to build toggles and guided navigation.
        • 
    
      
    
      Conditional formatting
      
    
      Background colour, data bars and icons in tables and matrices draw the eye to exceptions. Use them for one purpose per table. If everything is highlighted, nothing is.
      
  
      
  
      Straight talk. It is tempting to show how much work went in by putting everything on the page. Readers experience that as clutter. The harder and kinder choice is to cut. If a visual does not help answer the page's question, move it to a detail page or remove it. Your report will look like less and be used more.

  Module 6 · Power BI service · 1.5 hrs
  
      Publish, refresh and secure
      
  
      A report on your laptop helps one person. Publishing puts it where others can use it, keeps it current without you, and controls who sees what.
      
  
        
    
      • Publish to a workspace and share through an app
        • 
    
      • Schedule refresh, with a gateway when needed
        • 
    
      • Restrict rows with row-level security
        • 
    
      • Know what to check before you share
        • 
  
      
  
      
    
      From Desktop to the service
      
    
        
      
      • Publish from Power BI Desktop sends two items to a workspace: the semantic model (your tables, relationships and measures) and the report built on it.
        • 
      
      • A workspace is where a team builds and maintains content. Roles are Admin, Member, Contributor and Viewer.
        • 
      
      • An app packages finished reports from a workspace for readers. It is the clean way to distribute to a large audience.
        • 
      
      • One semantic model can feed many reports. Build the model once and let others connect to it instead of copying the file.
        • 
    
      
    
      Keeping data fresh
      
    
        
      
      • Set scheduled refresh in the semantic model's settings and enter credentials for each source.
        • 
      
      • Cloud sources refresh directly. Sources inside your network, such as an on-premises SQL Server or a file share, need an on-premises data gateway.
        • 
      
      • Files on SharePoint or OneDrive refresh without a gateway. Connect to them by web path, not a local C:\ path.
        • 
      
      • For large fact tables, incremental refresh reloads only recent periods. It uses two Power Query parameters named RangeStart and RangeEnd.
        • 
      
      • Turn on refresh failure notifications so you hear about a problem before your readers do.
        • 
    
      
    
      Row-level security
      
    
      Row-level security (RLS) limits which rows a person can see. Define roles in Desktop (Modeling → Manage roles) with a DAX filter on a table, then assign people or groups to each role in the service.
      
  
      

      -- Static role: one role per region
Region[Region] = "East"

-- Dynamic role: one role for everyone, driven by a mapping table
SalesRep[Email] = USERPRINCIPALNAME ()
      
  
      
    
      Test with "View as" before publishing. RLS applies to viewers; people with edit rights on the workspace can see all the data.
      
    
      Import or DirectQuery?
      
    
      Import copies data into the model. It is fast and supports everything, and is the right default. DirectQuery leaves data in the source and queries it live, which suits very large or rapidly changing data at the cost of speed and some features. Start with Import unless you have a clear reason not to.
      
    
      Licensing
      
    
      Power BI Desktop is free. Sharing in the service generally requires paid licences for authors and readers, or capacity that covers readers. The plans and limits change, so confirm the current terms with your administrator before you promise anyone access.
      
    
      Before you share
      
    
        
      
      • Totals reconcile to a trusted source.
        • 
      
      • Refresh succeeds in the service, not only on your machine.
        • 
      
      • RLS has been tested as at least two different users.
        • 
      
      • The report states its data source and last refresh time.
        • 
      
      • Someone other than you has reviewed it.
        • 
    
      
  
      
  
      Straight talk. The first wrong number a senior person finds in your report costs more trust than ten good reports earn. That is a little unfair, and it is how it goes. Reconciling totals before publishing is dull work, and it is the work that makes people rely on you.
      
  
      
    
      Do it for real
      Your turn

        •

  Module 7 · Patterns · 1 hr
  
      Common uses, and how each is built
      
  
      Most business reports are variations on a small set of patterns. Each card names the Power Query work, the model shape and the key measure, so you can recognise your own problem and know where to start.
      
  
      
  
      
  
      Straight talk. You do not need a grand project to begin. Pick the one report you rebuild by hand most often, the one you quietly dread, and automate that. A small win that gives you two hours back every month is a better start than an ambitious dashboard that never ships.
      
  
      

      



      
  Module 8 · Capstone · 4–6 hrs
  
      Build one report end to end
      
  
      Take one real question from your own work and carry it through every stage. This is the piece of work that turns the course into a skill.
      
  
      
    
      The brief
      
    
      Choose a question someone asks regularly, such as "How are sales tracking against last year, and where are we behind?" Build a published report that answers it and refreshes without manual steps.
      
  
      
  
      
    
      Checklist
      What done looks like
      
    
        
      
      • The question and the audience are written down in one sentence each.
        • 
      
      • Data loads from the raw source with no manual clean-up beforehand.
        • 
      
      • Every Power Query step has a meaningful name and every column a deliberate type.
        • 
      
      • The model is a star: one or more facts, separate dimensions, a marked date table.
        • 
      
      • All relationships are one-to-many, single direction.
        • 
      
      • At least five measures, including one ratio with DIVIDE and one time comparison.
        • 
      
      • Two measures have been checked by hand against the source.
        • 
      
      • A summary page answers the question in under ten seconds.
        • 
      
      • A drillthrough page gives the detail behind any summary figure.
        • 
      
      • The report is published, refresh is scheduled, and one other person has used it and given feedback.
